# Тестовое задание — AI Generalist / AI Automation Specialist

Репозиторий содержит две части тестового задания:

1. **Лендинг-портфолио** — показывает мой опыт и подход к разработке в контексте вакансии.
2. **Навигатор поставщиков** — прототип сервиса для поиска, сравнения и приоритизации поставщиков продуктов питания.

Основная идея обеих частей — показать не отдельную технологию, а полный цикл работы: от понимания задачи и проектирования до реализации, тестирования и запуска.

# Часть 2. Навигатор поставщиков

## Задача и продуктовая идея

При ручном поиске поставщиков закупщик обычно открывает много сайтов, отдельно ищет контакты, условия доставки, минимальный заказ, цены и документы, а затем переносит всё это в таблицу и вручную сравнивает варианты.

Цель прототипа — сократить этот путь до одного рабочего сценария:

```text
Запрос пользователя
        ↓
Поиск кандидатов
        ↓
Сбор и нормализация информации
        ↓
Сохранение источника и даты проверки
        ↓
Объяснимое ранжирование
        ↓
Сравнение поставщиков
        ↓
Контакт / заметка / экспорт
```

Сервис отвечает не только на вопрос **«какие поставщики существуют?»**, но и помогает понять **«с кем имеет смысл связаться первым?»**.

## Что реализовано

Пользователь может:

- искать поставщиков по категории товара;
- указывать город или регион;
- учитывать необходимость доставки;
- повышать приоритет поставщиков с информацией о сертификатах;
- работать с подготовленным каталогом без внешних API;
- при необходимости включить поиск новых сайтов в интернете;
- видеть контакты и официальный сайт поставщика;
- видеть источник, из которого получены данные, и дату его проверки;
- просматривать MOQ, ориентир по цене, документы, доставку и регион работы;
- видеть рейтинг поставщика от 0 до 100 и причины, повлиявшие на оценку;
- сохранять собственные заметки;
- добавлять поставщиков в избранное;
- выбирать до трёх поставщиков и сравнивать их в одной таблице;
- экспортировать результаты в CSV и XLSX;
- работать с API через автоматически сформированную OpenAPI-документацию.

## Почему здесь используется AI

AI применяется только на этапе, где обычные правила быстро становятся хрупкими: при извлечении фактов из неструктурированных страниц поставщиков.

Один сайт может написать:

> Минимальный заказ — 30 000 ₽.

Другой:

> Отгрузка осуществляется партиями от пяти коробов.

Третий разместит нужную информацию внутри общего текста раздела о доставке. Жёсткий парсер потребует всё больше отдельных правил для разных формулировок.

Поэтому при включённом поиске новых сайтов схема выглядит так:

```text
Поисковый запрос
        ↓
Найденные сайты
        ↓
HTTP-загрузка страницы
        ↓
Очистка HTML
        ↓
LLM
        ↓
Строгая JSON-схема
        ↓
Проверка и сохранение
```

LLM получает текст страницы и должна извлечь только явно присутствующие факты: название, категорию, географию, контакт, MOQ, цену, сертификаты и условия доставки.

Ключевое правило системной инструкции: **если информации нет на странице, значение должно остаться неизвестным, а не быть придумано моделью**.

## Почему AI не принимает итоговое решение

Рейтинг поставщиков намеренно рассчитывается обычным Python-кодом, а не LLM.

Это делает результат:

- повторяемым;
- объяснимым;
- тестируемым;
- управляемым с точки зрения бизнес-правил.

Текущая система весов является продуктовой гипотезой:

| Критерий | Вклад |
| --- | ---: |
| Совпадение категории | до 35 |
| Точное совпадение города | 20 |
| Совпадение региона | 14 |
| Проверенный контакт из исходного каталога | 8 |
| Публичный ориентир по цене | 6 |
| Известный MOQ | 5 |
| Информация о доставке | 5 + дополнительный приоритет по запросу |
| Информация о сертификатах | 5 + дополнительный приоритет по запросу |
| Полнота карточки | до 10 |

В интерфейсе вместе с оценкой показываются причины, например: «категория совпадает», «работает в выбранном городе», «есть информация о доставке».

В рабочем продукте веса следует корректировать по фактической обратной связи закупщиков: с каким поставщиком связались, от кого получили предложение и кто в итоге был выбран.

## Источник данных и официальный сайт

В карточке разделены два понятия:

- **Официальный сайт** — сайт самого поставщика, куда можно перейти для дальнейшей работы с компанией.
- **Источник данных** — конкретная страница, по которой сервис сформировал или подтвердил информацию карточки.

Так пользователь может не только увидеть коммерческий факт, но и проверить, откуда он был получен.

Для внешних данных также сохраняется дата проверки, потому что цена, MOQ, условия доставки и ассортимент со временем меняются.


### 1. Поиск новых сайтов

В интерфейсе можно включить флаг **«Искать новые сайты в интернете»**.

Прототип формирует поисковый запрос по категории и географии, получает кандидатов, исключает нерелевантные агрегаторы и пытается обработать несколько найденных сайтов.

Если задан `LLM_API_KEY`, страницы разбираются через LLM. Если ключ не настроен, сервис использует резервное извлечение по правилам, поэтому приложение остаётся работоспособным и без AI-доступа.

В текущем прототипе для демонстрации используется HTML-выдача DuckDuckGo. В промышленной версии этот этап целесообразно заменить на официальный поисковый API или специализированного поставщика данных.

## Архитектура

```text
Браузер
   ↓ HTTP
FastAPI
   ├── поиск и фильтрация
   ├── заметки
   ├── экспорт CSV/XLSX
   ├── ранжирование
   └── веб-поиск и обогащение
            ↓
      HTTP + BeautifulSoup
            ↓
      LLM / резервные правила
            ↓
        SQLAlchemy
            ↓
   PostgreSQL / SQLite
```

### Backend

**FastAPI** выбран как основной HTTP-слой, потому что он подходит для API-сервиса на Python, удобно работает с асинхронными внешними HTTP-запросами и автоматически предоставляет OpenAPI.

**Pydantic** задаёт контракты входных и выходных данных и ограничения, например длину заметок и количество экспортируемых поставщиков.

**SQLAlchemy** используется для доступа к БД и отделяет прикладную логику от конкретной СУБД.

### Хранение данных

При запуске через Docker используется **PostgreSQL**.

При локальном запуске без Docker по умолчанию используется **SQLite**, чтобы проект можно было быстро проверить без отдельной настройки БД.

Основная сущность `Supplier` хранит:

- название;
- категорию;
- город и регион;
- сайт и контакт;
- MOQ;
- ориентир по цене;
- сертификаты;
- доставку;
- пользовательскую заметку;
- источник;
- дату проверки;
- полноту карточки;
- признак вручную проверенного контакта.

## Запуск через Docker

Это основной и самый простой способ проверки второй части.

Перейти в папку:

```bash
cd supplier-scout
```

Запустить приложение и PostgreSQL:

```bash
docker compose up --build
```

После запуска:

- интерфейс: `http://127.0.0.1:8000`;
- OpenAPI/Swagger: `http://127.0.0.1:8000/docs`;
- проверка состояния: `http://127.0.0.1:8000/health`.

Остановить контейнеры:

```bash
docker compose down
```

Если требуется удалить и данные PostgreSQL из Docker volume:

```bash
docker compose down -v
```

## Запуск с LLM

Без ключа приложение полностью запускается и работает с локальным каталогом. Веб-поиск также может использовать резервные правила извлечения.

Для LLM-извлечения создать `.env` в папке `supplier-scout`:

```env
LLM_API_KEY=ваш_ключ
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-4.1-mini
```

Пример находится в `.env.example`.

После этого снова запустить:

```bash
docker compose up --build
```

В `/health` поле `ai` показывает, передан ли приложению ключ LLM.

## Локальный запуск без Docker

При необходимости сервис можно запустить напрямую на Python. В этом режиме по умолчанию используется SQLite.

```bash
cd supplier-scout
python -m venv .venv
```

Windows:

```powershell
.venv\Scripts\activate
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Установка зависимостей и запуск:

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Открыть:

```text
http://127.0.0.1:8000
```

## Как проверить основной сценарий

1. Открыть главную страницу.
2. Ввести категорию, например `овощи`.
3. Указать `Екатеринбург`.
4. При необходимости включить «Нужна доставка» и «Важны сертификаты».
5. Нажать «Найти поставщиков».
6. Посмотреть рейтинг и причины оценки.
7. Открыть официальный сайт или источник данных.
8. Добавить поставщика в избранное.
9. Выбрать 2–3 карточки и открыть сравнение.
10. Добавить заметку к поставщику.
11. Экспортировать список или сравнение в CSV/XLSX.
12. При наличии доступа к внешней сети включить «Искать новые сайты в интернете».

## Тестирование

Запуск тестов из `supplier-scout`:

```bash
pytest -q
```

Набор unit-тестов проверяет ключевые части, которые должны быть детерминированными:

- расчёт рейтинга;
- совпадение города и региона;
- влияние проверенного контакта;
- очистку URL поисковой выдачи;
- фильтрацию агрегаторов;
- извлечение телефона и email резервными правилами;
- извлечение условий доставки;
- формирование CSV;
- формирование XLSX;
- ограничения входных Pydantic-схем.

Внешний интернет и ответы LLM не используются как обязательное условие unit-тестов, чтобы тестовый набор оставался воспроизводимым.

## Обработка ошибок

Сбой одного внешнего сайта не должен останавливать весь поиск. Ошибки загрузки и разбора отдельных источников логируются, после чего обработка остальных кандидатов продолжается.

Если сам веб-поиск недоступен, сервис возвращается к уже сохранённому каталогу и сообщает используемый режим в интерфейсе.

## Ограничения текущего прототипа

Это MVP, поэтому в нём осознанно не реализованы некоторые элементы промышленной системы:

- фоновые очереди для длительного сбора данных;
- авторизация и рабочие пространства компаний;
- полноценная дедупликация поставщиков по ИНН, телефону и домену;
- отдельная история изменения каждого коммерческого факта;
- автоматическое расписание повторной проверки источников;
- официальный поисковый API;
- полноценная система confidence/evidence для каждого извлечённого поля.

## Итог

В прототипе AI намеренно является частью общей системы, а не её заменой. LLM решает задачу понимания неструктурированного текста, тогда как API, хранение данных, валидация, рейтинг, заметки, сравнение и экспорт реализованы обычным кодом.

Такое разделение позволяет использовать сильные стороны AI там, где они действительно полезны, при этом сохранить предсказуемость и объяснимость ключевой бизнес-логики.
