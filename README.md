# Тестовое задание — AI Generalist / AI Automation Specialist

Репозиторий содержит две части тестового задания:

1. **Лендинг-портфолио** — показывает мой опыт и подход к разработке в контексте вакансии.
2. **Навигатор поставщиков** — прототип сервиса для поиска, сравнения и приоритизации поставщиков продуктов питания.

Основная идея обеих частей — показать не отдельную технологию, а полный цикл работы: от понимания задачи и проектирования до реализации, тестирования и запуска.

# Часть 2. Навигатор поставщиков

## Задача и продуктовая идея

При ручном поиске поставщиков закупщик обычно открывает много сайтов, отдельно ищет контакты, условия доставки, минимальный заказ, цены и документы, а затем переносит всё это в таблицу и вручную сравнивает варианты.

Цель прототипа — сократить этот путь до одного рабочего сценария:

```text
Запрос пользователя
        ↓
Поиск кандидатов
        ↓
Сбор и нормализация информации
        ↓
Сохранение источника и даты проверки
        ↓
Объяснимое ранжирование
        ↓
Сравнение поставщиков
        ↓
Контакт / заметка / экспорт
```

Сервис отвечает не только на вопрос **«какие поставщики существуют?»**, но и помогает понять **«с кем имеет смысл связаться первым?»**.

## Что реализовано

Пользователь может:

- искать поставщиков по категории товара;
- указывать город или регион;
- учитывать необходимость доставки;
- повышать приоритет поставщиков с информацией о сертификатах;
- работать с подготовленным локальным каталогом без внешних API;
- при наличии `LLM_API_KEY` включать поиск новых поставщиков в интернете;
- видеть контакты и официальный сайт поставщика;
- видеть источник, из которого получены данные, и дату его проверки;
- просматривать MOQ, ориентир по цене, документы, доставку и регион работы;
- видеть рейтинг поставщика от 0 до 100 и причины, повлиявшие на оценку;
- сохранять собственные заметки;
- добавлять поставщиков в избранное;
- выбирать до трёх поставщиков и сравнивать их в одной таблице;
- экспортировать результаты в CSV и XLSX;
- работать с API через автоматически сформированную OpenAPI-документацию.

Если по введённой категории нет совпадений, сервис не подмешивает нерелевантные записи из локального каталога: пользователь получает пустой результат либо поставщиков, найденных через веб-поиск.

## Почему здесь используется AI

AI применяется в той части процесса, где обычные правила быстро становятся хрупкими: при поиске новых поставщиков и извлечении фактов из неструктурированных веб-источников.

Один сайт может написать:

> Минимальный заказ — 30 000 ₽.

Другой:

> Отгрузка осуществляется партиями от пяти коробов.

Третий разместит нужную информацию внутри общего текста раздела о доставке.

Вместо собственного скрейпинга поисковой выдачи прототип использует **OpenAI Responses API** со встроенным инструментом **Web Search**. Модель получает поисковую задачу, находит релевантные источники и возвращает нормализованные данные по строгой JSON-схеме.

Схема при включённом веб-поиске выглядит так:

```text
Запрос пользователя
        ↓
OpenAI Responses API
        ↓
Web Search
        ↓
Поиск и чтение релевантных источников
        ↓
LLM
        ↓
Structured Outputs / JSON Schema
        ↓
Проверка и сохранение
        ↓
Детерминированный рейтинг
```

Для каждого найденного поставщика модель должна вернуть:

- название;
- категорию;
- город и регион;
- официальный сайт;
- контакт;
- MOQ;
- ориентир по цене;
- сертификаты или документы;
- условия доставки;
- URL источника.

Ключевое правило запроса к модели: **извлекать только явно подтверждаемые факты**. Если информации нет, поле должно оставаться неизвестным, а не заполняться догадкой.

Ответ LLM дополнительно ограничен строгой JSON-схемой (`Structured Outputs`), поэтому backend получает предсказуемую структуру данных, а не свободный текст.

## Почему AI не принимает итоговое решение

Рейтинг поставщиков намеренно рассчитывается обычным Python-кодом, а не LLM.

Это делает результат:

- повторяемым;
- объяснимым;
- тестируемым;
- управляемым с точки зрения бизнес-правил.

Текущая система весов является продуктовой гипотезой:

| Критерий | Вклад |
| --- | ---: |
| Совпадение категории | до 35 |
| Точное совпадение города | 20 |
| Совпадение региона | 14 |
| Проверенный контакт из исходного каталога | 8 |
| Публичный ориентир по цене | 6 |
| Известный MOQ | 5 |
| Информация о доставке | 5 + дополнительный приоритет по запросу |
| Информация о сертификатах | 5 + дополнительный приоритет по запросу |
| Полнота карточки | до 10 |

В интерфейсе вместе с оценкой показываются причины, например: «категория совпадает», «работает в выбранном городе», «есть информация о доставке».

В рабочем продукте веса следует корректировать по фактической обратной связи закупщиков: с каким поставщиком связались, от кого получили предложение и кто в итоге был выбран.

## Источник данных и официальный сайт

В карточке разделены два понятия:

- **Официальный сайт** — сайт самого поставщика, куда можно перейти для дальнейшей работы с компанией.
- **Источник данных** — конкретная страница, на основании которой сервис сформировал карточку или подтвердил её данные.

Так пользователь может не только увидеть коммерческий факт, но и проверить, откуда он был получен.

Для внешних данных сохраняется дата проверки, потому что цена, MOQ, условия доставки и ассортимент со временем меняются.

## Поиск новых поставщиков

В интерфейсе можно включить флаг **«Искать новые сайты в интернете»**.

Если `LLM_API_KEY` настроен, backend отправляет категорию и географию в OpenAI Responses API с инструментом `web_search`. Модель ищет релевантные компании, по возможности использует официальные сайты и возвращает до нескольких нормализованных карточек.

Маркетплейсы, доски объявлений и информационные агрегаторы исключаются инструкцией поиска: цель — получить именно поставщика и подтверждающий источник, а не список посредников.

Найденные карточки сохраняются в БД и участвуют в том же детерминированном ранжировании, что и локальный каталог.

Если ключ не настроен или внешний AI-сервис временно недоступен, приложение не падает: оно продолжает работать с релевантными записями локального каталога и сообщает используемый режим в интерфейсе.

## Архитектура

```text
Браузер
   ↓ HTTP
FastAPI
   ├── поиск и фильтрация
   ├── заметки
   ├── экспорт CSV/XLSX
   ├── ранжирование
   └── поиск новых поставщиков
            ↓
      OpenAI Responses API
            ↓
        Web Search + LLM
            ↓
       Structured Outputs
            ↓
        SQLAlchemy
            ↓
   PostgreSQL / SQLite
```

### Backend

**FastAPI** выбран как основной HTTP-слой, потому что подходит для API-сервиса на Python, удобно работает с асинхронными внешними HTTP-запросами и автоматически предоставляет OpenAPI.

**Pydantic** задаёт контракты входных и выходных данных. Для входных API-схем включён строгий режим: неизвестные поля отклоняются с ошибкой валидации, а не игнорируются молча.

**SQLAlchemy** используется для доступа к БД и отделяет прикладную логику от конкретной СУБД.

### Хранение данных

При запуске через Docker Compose используется **PostgreSQL**.

При локальном запуске без отдельной конфигурации по умолчанию используется **SQLite**, чтобы проект можно было быстро проверить без настройки внешней БД.

Основная сущность `Supplier` хранит:

- название;
- категорию;
- город и регион;
- сайт и контакт;
- MOQ;
- ориентир по цене;
- сертификаты;
- доставку;
- пользовательскую заметку;
- источник;
- дату проверки;
- полноту карточки;
- признак вручную проверенного контакта.

Автоматически найденный контакт не получает признак `verified_contact`: этот флаг оставлен только для контактов, проверенных в исходном демонстрационном каталоге.

## Запуск через Docker

Это основной способ локальной проверки второй части.

Перейти в папку:

```bash
cd supplier-scout
```

Запустить приложение и PostgreSQL:

```bash
docker compose up --build
```

После запуска:

- интерфейс: `http://127.0.0.1:8000`;
- OpenAPI/Swagger: `http://127.0.0.1:8000/docs`;
- проверка состояния: `http://127.0.0.1:8000/health`.

Остановить контейнеры:

```bash
docker compose down
```

Если требуется удалить данные PostgreSQL из Docker volume:

```bash
docker compose down -v
```

## Запуск с AI и веб-поиском

Без ключа приложение полностью запускается и работает с локальным каталогом.

Для поиска новых поставщиков создать `.env` в папке `supplier-scout`:

```env
LLM_API_KEY=ваш_ключ
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-4.1-mini
```

Шаблон находится в `.env.example`.

После этого снова запустить:

```bash
docker compose up --build
```

В `/health` поле `ai` показывает, передан ли приложению ключ.

При публичном развёртывании ключ должен храниться только в переменных окружения платформы и не должен попадать в Git-репозиторий.

## Локальный запуск без Docker

При необходимости сервис можно запустить напрямую на Python. В этом режиме по умолчанию используется SQLite.

```bash
cd supplier-scout
python -m venv .venv
```

Windows:

```powershell
.venv\Scripts\activate
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Установка зависимостей и запуск:

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Открыть:

```text
http://127.0.0.1:8000
```

## Как проверить основной сценарий

1. Открыть главную страницу.
2. Ввести категорию, например `овощи`.
3. Указать `Екатеринбург`.
4. При необходимости включить «Нужна доставка» и «Важны сертификаты».
5. Нажать «Найти поставщиков».
6. Посмотреть рейтинг и причины оценки.
7. Открыть официальный сайт или источник данных.
8. Добавить поставщика в избранное.
9. Выбрать 2–3 карточки и открыть сравнение.
10. Добавить заметку к поставщику.
11. Экспортировать список или сравнение в CSV/XLSX.
12. При настроенном `LLM_API_KEY` включить «Искать новые сайты в интернете» и выполнить запрос по категории, которой нет в локальном каталоге, например `моцарелла`.

Если веб-поиск успешно отработал, интерфейс покажет режим:

```text
OpenAI Web Search + извлечение фактов через LLM
```

и количество найденных новых источников.

## API

Основные маршруты:

```text
GET    /health
POST   /api/search
GET    /api/suppliers/{id}
PATCH  /api/suppliers/{id}/notes
POST   /api/export/csv
POST   /api/export/xlsx
```

Пример запроса к поиску:

```json
{
  "category": "моцарелла",
  "geography": "Екатеринбург",
  "need_delivery": true,
  "need_certificates": true,
  "live_search": true,
  "limit": 10
}
```

Неизвестные поля API отклоняются Pydantic-валидацией. Например, `require_delivery` вместо `need_delivery` вернёт ошибку `422`, а не будет проигнорирован.

## Тестирование

Запуск тестов из `supplier-scout`:

```bash
pytest -q
```

Набор unit-тестов проверяет ключевые части, которые должны быть детерминированными:

- расчёт рейтинга;
- совпадение города и региона;
- влияние проверенного контакта;
- разбор структурированного ответа OpenAI Responses API;
- фильтрацию некорректных URL источников;
- формирование CSV;
- формирование XLSX;
- ограничения входных Pydantic-схем;
- запрет неизвестных полей API.

Внешний интернет и реальные ответы LLM не используются как обязательное условие unit-тестов, чтобы тестовый набор оставался быстрым и воспроизводимым.

## Обработка ошибок

Сбой внешнего AI-сервиса не должен останавливать работу приложения. Тип исключения, HTTP-статус и ограниченный фрагмент ответа внешнего API логируются, после чего сервис возвращает релевантные записи локального каталога, если они существуют.

Если по введённой категории нет ни локальных, ни найденных внешних поставщиков, API возвращает пустой список. Нерелевантные компании из других категорий больше не используются как запасной результат.

## Ограничения текущего прототипа

Это MVP, поэтому в нём осознанно не реализованы некоторые элементы промышленной системы:

- фоновые очереди для длительного сбора данных;
- авторизация и рабочие пространства компаний;
- полноценная дедупликация поставщиков по ИНН, телефону и домену;
- отдельная история изменения каждого коммерческого факта;
- автоматическое расписание повторной проверки источников;
- отдельный evidence/confidence для каждого извлечённого поля;
- ручная модерация новых автоматически найденных поставщиков перед публикацией в общем каталоге;
- метрики качества поиска и обратная связь закупщиков для обучения весов ранжирования.

## Итог

В прототипе AI намеренно является частью общей системы, а не её заменой. OpenAI Web Search и LLM решают задачу поиска и понимания неструктурированной информации, тогда как API, хранение данных, валидация, рейтинг, заметки, сравнение и экспорт реализованы обычным кодом.

Такое разделение позволяет использовать сильные стороны AI там, где они действительно полезны, и сохранить предсказуемость, объяснимость и тестируемость ключевой бизнес-логики.
