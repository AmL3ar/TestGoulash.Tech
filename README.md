# Тестовое задание — AI Generalist / AI Automation Specialist

Репозиторий содержит две части тестового задания:

1. **Лендинг-портфолио** — показывает мой опыт и подход к разработке в контексте вакансии.
2. **Навигатор поставщиков** — прототип сервиса для поиска, сравнения и приоритизации поставщиков продуктов питания.

Основная идея обеих частей — показать не отдельную технологию, а полный цикл работы: от понимания задачи и проектирования до реализации, тестирования и запуска.

Для второй части оставлены две реализации одного пользовательского сценария:

- `supplier-scout/` — основной вариант с OpenAI Web Search и LLM-извлечением;
- `supplier-scout-no-llm/` — полностью бесплатный вариант без LLM, где веб-страницы разбираются обычным кодом.

Это позволяет показать границу применимости AI: интерфейс, API, БД, рейтинг, заметки, сравнение и экспорт в обеих версиях остаются обычным детерминированным кодом; отличается только способ поиска и извлечения внешних данных.

## Структура репозитория

```text

├── portfolio/                  # Часть 1. Лендинг-портфолио
```

# Часть 2. Навигатор поставщиков

## Задача и продуктовая идея

При ручном поиске поставщиков закупщик обычно открывает много сайтов, отдельно ищет контакты, условия доставки, минимальный заказ, цены и документы, а затем переносит всё это в таблицу и вручную сравнивает варианты.

Цель прототипа — сократить этот путь до одного рабочего сценария:

```text
Запрос пользователя
        ↓
Поиск кандидатов
        ↓
Сбор и нормализация информации
        ↓
Сохранение источника и даты проверки
        ↓
Объяснимое ранжирование
        ↓
Сравнение поставщиков
        ↓
Контакт / заметка / экспорт
```

Сервис отвечает не только на вопрос **«какие поставщики существуют?»**, но и помогает понять **«с кем имеет смысл связаться первым?»**.

## Что реализовано

Пользователь может:

- искать поставщиков по категории товара;
- указывать город или регион;
- учитывать необходимость доставки;
- повышать приоритет поставщиков с информацией о сертификатах;
- работать с подготовленным каталогом без внешних API;
- при необходимости включить поиск новых сайтов в интернете;
- видеть контакты и официальный сайт поставщика;
- видеть источник, из которого получены данные, и дату его проверки;
- просматривать MOQ, ориентир по цене, документы, доставку и регион работы;
- видеть рейтинг поставщика от 0 до 100 и причины, повлиявшие на оценку;
- сохранять собственные заметки;
- добавлять поставщиков в избранное;
- выбирать до трёх поставщиков и сравнивать их в одной таблице;
- экспортировать результаты в CSV и XLSX;
- работать с API через автоматически сформированную OpenAPI-документацию.

Если поставщик по введённой категории не найден, сервис возвращает пустой результат, а не подмешивает нерелевантные компании из каталога.

## Две реализации внешнего поиска

### Основная версия с AI — `supplier-scout/`

AI используется на этапе, где обычные правила быстро становятся хрупкими: при поиске и нормализации информации из неоднородных публичных источников.

Схема внешнего поиска:

```text
Категория + география
        ↓
OpenAI Responses API
        ↓
Web Search
        ↓
Структурированный ответ по JSON Schema
        ↓
Проверка и сохранение
        ↓
Детерминированный рейтинг
```

Модель получает задачу найти релевантных поставщиков и вернуть только подтверждаемые поля: название, категорию, географию, официальный сайт, контакт, MOQ, ориентир по цене, сертификаты, доставку и конкретный `source_url`.

Ключевое правило: **если конкретный факт не подтверждается источником, поле должно остаться неизвестным, а не быть придумано моделью**.

Structured Outputs используются для того, чтобы результат соответствовал заранее заданной JSON-схеме до сохранения в БД.

### Версия без LLM — `supplier-scout-no-llm/`

Эта версия сохраняет тот же интерфейс и бизнес-логику, но не использует нейросетевой API.

Схема:

```text
Категория + география
        ↓
Google Search API через Serper
        ↓
Ссылки на сайты поставщиков
        ↓
HTTP-загрузка страниц
        ↓
BeautifulSoup
        ↓
Регулярные выражения + словарные правила
        ↓
Структурированная карточка
        ↓
Детерминированный рейтинг
```

Телефоны и email извлекаются регулярными выражениями. Для MOQ, цены, доставки и документов ищутся предложения с характерными ключевыми словами, например `минимальный заказ`, `прайс`, `доставка`, `сертификат`, `декларация`.

Для стабильного поиска кандидатов версия без LLM поддерживает Google-выдачу через Serper Search API. Нейросеть при этом не используется: Search API возвращает обычные результаты поиска, а дальнейшее извлечение данных выполняется локальным Python-кодом через BeautifulSoup, регулярные выражения и словарные правила.

`SERPER_API_KEY` является необязательным. Если ключ не задан или внешний API временно недоступен, сервис последовательно пробует резервные публичные источники: Bing RSS, Bing HTML и DuckDuckGo HTML. Это позволяет сохранить работоспособность прототипа, но наиболее воспроизводимый live-поиск получается именно через Search API.

## Почему оставлены обе версии

Основная архитектура проекта предполагает AI-сценарий. На момент подготовки публичного демо OpenAI API-ключ подключён корректно, однако на API-аккаунте отсутствует оплаченный баланс. В этом состоянии OpenAI возвращает HTTP `429` с кодом `credit_balance_exhausted` / `insufficient_quota`.

Это ограничение относится к биллингу внешнего API, а не к запуску приложения: локальный каталог, рейтинг, сравнение, заметки, экспорт, Swagger и остальные функции основной версии продолжают работать без внешнего запроса.

Чтобы проверяющий мог протестировать внешний поиск **без OpenAI-кредитов**, рядом оставлена версия `supplier-scout-no-llm/`. Она решает ту же задачу без нейросети. Для стабильного live-поиска можно передать бесплатный `SERPER_API_KEY`; без него сервис использует резервные публичные источники. Локальный каталог остаётся независимым сценарием и не требует внешних сервисов.

После пополнения API-баланса основная AI-версия не требует изменений кода: достаточно передать рабочий `LLM_API_KEY`.

## Почему AI не принимает итоговое решение

Рейтинг поставщиков намеренно рассчитывается обычным Python-кодом, а не LLM.

Это делает результат:

- повторяемым;
- объяснимым;
- тестируемым;
- управляемым с точки зрения бизнес-правил.

Текущая система весов является продуктовой гипотезой:

| Критерий | Вклад |
| --- | ---: |
| Совпадение категории | до 35 |
| Точное совпадение города | 20 |
| Совпадение региона | 14 |
| Проверенный контакт из исходного каталога | 8 |
| Публичный ориентир по цене | 6 |
| Известный MOQ | 5 |
| Информация о доставке | 5 + дополнительный приоритет по запросу |
| Информация о сертификатах | 5 + дополнительный приоритет по запросу |
| Полнота карточки | до 10 |

В интерфейсе вместе с оценкой показываются причины, например: «категория совпадает», «работает в выбранном городе», «есть информация о доставке».

В рабочем продукте веса следует корректировать по фактической обратной связи закупщиков: с каким поставщиком связались, от кого получили предложение и кто в итоге был выбран.

## Источник данных и официальный сайт

В карточке разделены два понятия:

- **Официальный сайт** — сайт самого поставщика, куда можно перейти для дальнейшей работы с компанией.
- **Источник данных** — конкретная страница, по которой сервис сформировал или подтвердил информацию карточки.

Так пользователь может не только увидеть коммерческий факт, но и проверить, откуда он был получен.

Для внешних данных также сохраняется дата проверки, потому что цена, MOQ, условия доставки и ассортимент со временем меняются.

## Общая архитектура

```text
Браузер
   ↓ HTTP
FastAPI
   ├── поиск и фильтрация
   ├── заметки
   ├── экспорт CSV/XLSX
   ├── ранжирование
   └── получение внешних данных
          ├── AI: OpenAI Web Search + Structured Outputs
          └── без LLM: HTTP + BeautifulSoup + правила
                    ↓
                SQLAlchemy
                    ↓
           PostgreSQL / SQLite
```

### Backend

**FastAPI** используется как HTTP-слой: API остаётся небольшим, поддерживает асинхронные внешние запросы и автоматически предоставляет OpenAPI/Swagger.

**Pydantic** задаёт строгие контракты входных и выходных данных. Неизвестные поля запрещены: например, ошибочное `require_delivery` не будет молча проигнорировано вместо корректного `need_delivery`, а вернёт `422`.

**SQLAlchemy** используется для доступа к данным и позволяет запускать одну и ту же прикладную логику с SQLite и PostgreSQL.

### Хранение данных

При запуске через Docker используется **PostgreSQL**.

При локальном запуске без Docker по умолчанию используется **SQLite**, чтобы проект можно было быстро проверить без отдельной настройки БД.

Основная сущность `Supplier` хранит:

- название;
- категорию;
- город и регион;
- сайт и контакт;
- MOQ;
- ориентир по цене;
- сертификаты;
- доставку;
- пользовательскую заметку;
- источник;
- дату проверки;
- полноту карточки;
- признак вручную проверенного контакта.

# Запуск основной AI-версии

Перейти в папку:

```bash
cd supplier-scout
```

Запустить приложение и PostgreSQL:

```bash
docker compose up --build
```

После запуска:

- интерфейс: `http://127.0.0.1:8000`;
- OpenAPI/Swagger: `http://127.0.0.1:8000/docs`;
- проверка состояния: `http://127.0.0.1:8000/health`.

Остановить:

```bash
docker compose down
```

Для удаления Docker volume с БД:

```bash
docker compose down -v
```

## Подключение OpenAI

Создать `.env` в `supplier-scout`:

```env
LLM_API_KEY=ваш_ключ
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-4.1-mini
```

Затем снова выполнить:

```bash
docker compose up --build
```

В `/health` поле `ai` показывает, передан ли приложению ключ. Наличие ключа не гарантирует наличие API-кредитов: при нулевом балансе внешний запрос вернёт `429 insufficient_quota`, а приложение продолжит работу с локальными совпадениями.

# Как проверить основной сценарий

1. Открыть главную страницу.
2. Ввести категорию, например `овощи`.
3. Указать `Екатеринбург`.
4. При необходимости включить «Нужна доставка» и «Важны сертификаты».
5. Нажать «Найти поставщиков».
6. Посмотреть рейтинг и причины оценки.
7. Открыть официальный сайт или источник данных.
8. Добавить поставщика в избранное.
9. Выбрать 2–3 карточки и открыть сравнение.
10. Добавить заметку к поставщику.
11. Экспортировать список или сравнение в CSV/XLSX.
12. Для проверки внешнего поиска включить «Искать новые сайты в интернете».

В AI-версии шаг 12 требует работающего OpenAI API-баланса. В версии без LLM — нет.

## Обработка ошибок

Сбой одного внешнего источника не должен останавливать весь сценарий. Ошибка логируется, после чего сервис продолжает обработку доступных данных.

В AI-версии HTTP-ошибки OpenAI логируются вместе с типом исключения, статусом и фрагментом ответа. Например, отсутствие API-баланса явно отображается как `429 credit_balance_exhausted`.

Если внешний поиск недоступен, сервис показывает только релевантные локальные совпадения. При отсутствии совпадений возвращается пустой список — нерелевантные компании не добавляются в выдачу для заполнения интерфейса.

## Ограничения текущего прототипа

Это MVP, поэтому в нём осознанно не реализованы некоторые элементы промышленной системы:

- фоновые очереди для длительного сбора данных;
- авторизация и рабочие пространства компаний;
- полноценная дедупликация поставщиков по ИНН, телефону и домену;
- отдельная история изменения каждого коммерческого факта;
- автоматическое расписание повторной проверки источников;
- промышленная стратегия нескольких поисковых провайдеров и их мониторинга;
- полноценная система confidence/evidence для каждого извлечённого поля.

В no-LLM реализации Search API используется только для discovery — получения релевантных ссылок. Извлечение коммерческих фактов, валидация и ранжирование остаются детерминированными. Резервный парсинг публичной поисковой выдачи сохранён как fallback, но не рассматривается как основной production-механизм.

## Итог

В прототипе AI является частью общей системы, а не её заменой. В основной реализации он решает задачу поиска и нормализации неструктурированной внешней информации, тогда как API, хранение данных, валидация, рейтинг, заметки, сравнение и экспорт реализованы обычным кодом.

Отдельная версия без LLM показывает, что тот же бизнес-сценарий можно реализовать полностью детерминированно, но ценой более хрупкого извлечения и большего количества правил.

Такое разделение позволяет использовать сильные стороны AI там, где они действительно полезны, и при этом сохранять предсказуемость, объяснимость и возможность проверить основную продуктовую механику без платного AI API.
